1The the_content Read Path — a One-Way Pipeline

The front-end rendering chain registered in wp-includes/default-filters.php:201–210 is a strict, one-directional pipeline (like Array.reduce, not addEventListener). Each callback receives the previous callback's return value. Content appended at priority 20 never flows back through 8–11.

PriCallbackWhat it actually does
8apply_block_hooks_to_content_from_post_objectInjects plugin-declared "hooked blocks" into the markup string (tree mutation, no HTML yet)
9do_blocksParses block markup, runs render_callback for dynamic blocks — markup becomes HTML
10wptexturize · wpautop · shortcode_unautop · prepend_attachment · wp_replace_insecure_home_urlTypography ("→“, ...→…, skips pre/code), paragraph wrapping, <p> cleanup around shortcodes
11do_shortcodeDeliberately after wpautop so shortcode output escapes paragraph wrapping
12wp_filter_content_tagsLazy-loading / srcset for images & iframes
20convert_smiliesText emoticons → GIF images (runs last so generated HTML gets prettified too)
Priority is registration-order-sensitive at equal values: removing and re-adding wpautop at 10 silently moves it after shortcode_unautop — a real foot-gun when writing "conditional wpautop" guards.

2Shortcodes & the Hook API Internals

  • Paired shortcodes ([foo]body[/foo]) pass $content = $m[5] to the handler (wp-includes/shortcodes.php:432). No recursion — nested shortcodes require the handler to call do_shortcode($content) itself.
  • has_shortcode() short-circuits without [, verifies registration, recurses into inner content (shortcodes.php:149–169).
  • remove_filter() deletes one callback key from WP_Hook->callbacks[$priority]; the WP_Hook object itself is reused, not recreated (plugin.php:124–126).
  • make_clickable() (URL → <a>) is not on the_content by default.
Common plugin pattern remove_filter('the_content','wpautop') exists because wpautop at priority 10 has already run before your own priority-10 callback — a re-added copy is the only way to control it.

3Blocks — Static vs Dynamic, and Where Configuration Lives

Static block — core/paragraph

// wp-includes/blocks/paragraph.php:45
function register_block_core_paragraph() {
    register_block_type_from_metadata(
        __DIR__ . '/paragraph'   // no render_callback
    );
}
add_action( 'init', 'register_block_core_paragraph' );

Server outputs the stored HTML as-is; only render_block_core/paragraph filters touch it (e.g. auto-adding the wp-block-paragraph class).

Dynamic block — core/accordion

// wp-includes/blocks/accordion.php:41
register_block_type_from_metadata(
    __DIR__ . '/accordion',
    array(
      'render_callback' =>
        'render_block_core_accordion',
    )
);

do_blocks → WP_Block::render() executes the callback (class-wp-block.php:596). Unregistered block markup is not dynamic — its inner HTML still prints.

Block Hooks (priority 8) — "attach me automatically"

A plugin declares "blockHooks": { "core/post-content": "after" } in its block.json; apply_block_hooks_to_content_from_post_object() (blocks.php:1214) wraps the post in a temporary container block, inserts <!-- wp:myplugin/note /--> after it, then unwraps. Priority 8 runs before do_blocks precisely so the injected markup still gets rendered at 9.

Gutenberg is the historical project name; in code there is only core/paragraph-style block names. "Gutenberg blocks" = blocks.

4The pre_* Write Path — Input Sanitization Before INSERT

These fire only when an official write function runs (context 'db'), and never during reads:

The three-stage pipeline for short strings (default-filters.php:32–35)

  1. sanitize_text_field — invalid UTF-8 check, strip tags (nukes script/style blocks whole), collapse [\r\n\t ]+, trim, remove all %xx encodings (formatting.php:5633)
  2. wp_filter_kses — whitelist filter using the narrow $allowedtags set (kses.php:602); post content uses the much wider $allowedposttags
  3. _wp_specialchars (pri 30) — & < > → entities, quotes untouched, no double-encoding
Every field has a mirrored pair: pre_term_name (save) vs term_name (display, admin-only hardening). Sanitize on write, defend-in-depth on read.

5Nonces — Proof of Intent, Not Permission

A nonce answers "did the current user's own browser deliberately send this?" while current_user_can() answers "may this user do it?". Cookies ride along on cross-site requests, so capability checks alone are CSRF-vulnerable. Both are required, nonce first.

SurfaceGenerateVerify
Admin formswp_nonce_field($action) functions.php:1899check_admin_referer() pluggable.php:1372
Link actionswp_nonce_url() functions.php:1868same

  • Missing nonce on a cookie-authenticated REST call → wp_set_current_user(0), the request silently becomes a guest (rest-api.php:1150) — the symptom is a misleading 403 "forbidden".
  • Hash input = tick | action | uid | session_token (pluggable.php:2533): logout, new session, or different action invalidates instantly.
  • Lifetime 24h in two 12h windows — wp_verify_nonce returns 1 (current) or 2 (previous) (:2486–2500).
  • Core echoes a fresh X-WP-Nonce response header on success (rest-api.php:1162); clients that never read it die after 24h.
Audit finding in the draftlab-ai-pro plugin: the admin JS takes the nonce once at page load and never refreshes it from response headers — any admin tab left open > 24 h starts throwing 403s until reload.

6Case Study: "Why Can't I Delete Two Header Tabs?"

The Happy Paws demo site combines a block theme (Twenty Twenty-Five) with an Elementor-built front page. That single fact explains every dead end:

Site Editor "导航栏" (wp_navigation #4)Header tabs actually shown (classic Menu #59)
StorageOne wp_posts row, content = block markup <!-- wp:page-list /-->wp_terms term + nav_menu_item posts + wp_postmeta + wp_term_relationships
RendererTheme patterns/header.php wp:navigation block (auto-created, page-list fallback)Elementor "WordPress Menu" widget (Unlimited Elements) bound to Menu
Edited whereSite Editor → NavigationAppearance → Menus — hidden because block themes register no menu locations

Why editing the Site Editor navigation did nothing: two parallel navigation systems with zero data linkage. The block-theme navigation renders only on templates the Elementor page doesn't override (404, archives).

Working removal paths

  • Borrow a classic theme's admin screen: activate Astra (registers locations, astra/inc/admin-functions.php:28) → Appearance → Menus reappears → remove items → switch back. Menu data is theme-independent.
  • Direct SQL (menu item IDs 9692, 9700): delete from wp_postmeta, wp_term_relationships, then wp_posts WHERE post_type='nav_menu_item' — three tables, never one.
Direct DB edits are viable when values are self-contained (menu items, post fields). Never hand-edit serialized option values (length prefixes break unserialize), password hashes, or denormalized counters.

7Tooling — Xdebug Under XAMPP

  • Install: php_xdebug-3.4.0-8.2-vs16-x86_64.dll → D:\xampp\php\ext\; php.ini gets zend_extension, xdebug.mode=debug, xdebug.start_with_request=trigger, port 9003.
  • Trigger mode beats always-on: without a listener, every page load would hang for seconds. Debugging starts only via ?XDEBUG_TRIGGER=1 (or the browser helper extension / cookie).
  • VS Code: PHP Debug (felixfbecker) extension, config "Listen for Xdebug", port 9003, no pathMappings needed locally.
  • Match the breakpoint to the execution path: do_blocks hits on front-end renders (the_content), not on the admin edit screen, whose REST context=edit returns raw stored content.
Watching $content transform from <!-- wp:paragraph -->… markup into final HTML inside do_blocks() is the fastest way to internalize the whole block pipeline.

8Key Takeaways

  • Read path vs write path: the_content runs per render; pre_* runs once per save. Two pipelines, two mental models.
  • Blocks = named, parameterized components. Registration = metadata + optional render_callback; the callback's presence is the entire static/dynamic distinction.
  • Everything visible but un-greppable lives in MySQL: menus, widgets, options, Elementor data. Search the database before doubting your grep.
  • Block theme ≠ no menus: it only hides the classic menu UI. The data and its consumers (Elementor, plugins) keep working.
  • Nonce ≠ capability; trigger-mode Xdebug ≠ broken Xdebug. Both "failures" were correct behavior waiting for the right invocation.
