经典主题 vs 块主题 & Elementor 接管

两种主题模型，一条 the_content 过滤器 —— 以及为什么 Elementor 渲染的页面没有块、没有锚点、Block Hooks 全部失效。

学习日期：2026-11-09  ·  本地实测：Astra 4.12.7（经典）· Twenty Twenty-Five（块）· Elementor 免费版
方法：读源码拿 file:line 证据 → 实测页面 HTML / 计算样式 → Xdebug 断点确认

1经典 vs 块主题 — 到底谁在造 HTML

同一个简单页面，肉眼看到的结果可能完全一样（表格块都输出 <table>），但机制完全不同：经典主题「执行 PHP」来拼骨架，块主题「存一段带块标记的文本」让解释器去渲染。

维度经典主题（Astra）块主题（TT5）
骨架归属主题 PHP（header.php、page.php）核心画布 wp-includes/template-canvas.php
结构存在哪代码文件 + Customizer 选项块标记文本（templates/*.html、parts/*.html，或库里覆盖）
导航数据nav_menu 分类法（term + nav_menu_item 文章）wp_navigation 文章类型
编辑入口Customizer + 外观 → 菜单站点编辑器

经典链路（Astra）

wp-includes/template-loader.php:132 执行 include $template; —— Astra 激活时就是 astra/page.php。astra/header.php:61 调用 astra_header() 打印页头标记；整个 <head>/<body> 文档就是手写的 PHP。菜单位置来自 astra/inc/admin-functions.php:28–43（register_nav_menus([primary, secondary_menu, mobile_menu])）—— 有了这个注册，「外观 → 菜单」这个界面才存在。绑定关系存在 theme_mods_astra 选项里：nav_menu_locations = { primary: 59, secondary_menu: 59 }。

块链路（Twenty Twenty-Five）

wp-includes/template.php:66 把解析出来的模板交给 locate_block_template()。wp-includes/block-template.php:65 用 current_theme_supports('block-templates') 判断 —— Astra 这里不通过，原样返回 PHP 路径；这个判断就是两个世界的分叉点。TT5 走块模板：模板文本存在 block-template.php:110 的 $_wp_current_template_content，block-template.php:138 返回的是 wp-includes/template-canvas.php（不是任何主题文件）。画布（template-canvas.php:12）调 get_the_block_template_html()，自己拼整个文档。

页头本身全是引用：twentytwentyfive/templates/page.html:1 → <!-- wp:template-part {"slug":"header"} /-->；twentytwentyfive/parts/header.html 只有一行 → <!-- wp:pattern {"slug":"twentytwentyfive/header"} /-->；真正的块在 twentytwentyfive/patterns/header.php:15–32 —— 一个 group，里面 core/site-title 和 core/navigation（第 24 行）。那个 wp:navigation 没有 ref，所以 WordPress 自动创建了一个 wp_navigation 文章（id 4），回退成页面列表。

一句话：经典页头是「PHP 代码在运行」，块页头是「文本被解释」。经典把结构放代码、数据放选项；块把结构本身变成可编辑的数据。

2中间的槽位归核心，框架归主题

不管哪种主题模型，正文槽位都由 core/post-content 产出：wp-includes/blocks/post-content.php:43 读取存储的 post_content，第 50 行执行 apply_filters('the_content', $content)。主题模板提供的是框架（wp_head、页头、页脚、全局样式）；核心执行 the_content 流水线填中间的槽位。这就是为什么内容不依赖主题的页面「换主题没变化」—— 中间完全相同，而一张普通表格几乎没有被主题样式化的表面。

3Elementor：通过它自己的 the_content 过滤器「发布」编译好的内容

Elementor（免费版、无 Theme Builder）不存块。设计稿存在 postmeta _elementor_data 里，post_content 几乎是空的。渲染时，Elementor 挂上 the_content，把整个值替换成它编译出的 HTML：

步骤位置发生了什么
优先级elementor/includes/frontend.php:33 + :324THE_CONTENT_FILTER_PRIORITY = 9；注册 apply_builder_in_content
替换frontend.php:1105–1110get_builder_content() 编译所有元素；$content = $builder_content —— 丢弃之前所有过滤器的产出
摘钩子frontend.php:1328–1341本轮链里移除 wpautop、shortcode_unautop、wptexturize（下次调用在 :1521–1527 恢复）

后果 1 — 输出里没有块，所以没有块锚点

最终 HTML 是 Elementor 编译的标记，不是块标记。按注册顺序 do_blocks（优先级 9）可能先跑了，但它的结果被整个替换掉。只存在于块形态里的东西 —— 块编辑器里设的块锚点 ID、块 wrapper、块样式 —— 在 Elementor 页面上根本不存在。

后果 2 — Block Hooks 永远活不下来

apply_block_hooks_to_content_from_post_object 在优先级 8，确实先执行、也能注入 <!-- wp:plugin/block /--> 标记。但到优先级 9 时 $content 被整体覆盖，注入全部作废。在 Elementor 渲染的页面上，Block Hooks 实际是空操作。

后果 3 — 排版过滤器被跳过，但短码 / srcset 还在跑

摘除名单恰好三个回调（frontend.php:1329–1333）：wpautop、shortcode_unautop、wptexturize。do_shortcode（11）、wp_filter_content_tags（12）、convert_smilies（20）没有被摘，仍会在 Elementor 的 HTML 上执行。

后果 4 — 主题仍然拥有框架

Elementor 只接管内容槽位。wp_head/wp_footer、主题 CSS、模板的页头页脚仍然来自主题；页面模板（Canvas 还是全宽）决定主题框架参不参与。

4案例 — 两套看起来像一套的导航系统

TT5 激活、首页由 Elementor 搭建时，页面上看到的顶部导航是 Elementor 小部件，绑定的是 nav_menu #59。站点编辑器里的「导航」实体是另一个东西：wp_navigation #4，由主题的页头 pattern 自动生成，回退成页面列表。在站点编辑器里改 #4，保存成功，但首页毫无变化 —— 因为首页渲染的压根不是它。

屏幕上看到的真实数据编辑入口
首页页头导航（Elementor）nav_menu #59外观 → 菜单（经典）/ 数据库
站点编辑器「导航」wp_navigation #4站点编辑器
Elementor 页面的正文_elementor_data postmetaElementor 编辑器
普通页面的正文post_content 块标记块编辑器
遇到「保存成功但页面没变」，第一个问题不是「缓存脏了吗」，而是「我改的数据，是渲染路径真正读的那份吗？」 Elementor 页面的答案是 _elementor_data + nav_menu，不是 post_content 块，也不是 wp_navigation。

5用 Xdebug 自己验证

  • 断在 wp-includes/template-loader.php:132，看 $template：Astra → themes/astra/page.php；TT5 → wp-includes/template-canvas.php（.html 文件从不会被 include —— 它是被当字符串读的）。
  • 断在 the_content 的过滤器循环，展开 $wp_filter['the_content']：这是一个运行时的订阅列表，不是固定的核心默认列表。插件在运行时加条目；同优先级按注册顺序执行。
  • 在 Elementor 页面上，单步进 frontend.php:1094 看 $content：第 1108 行被替换成编译后的 HTML；之后 has_filter('the_content','wpautop') 全程为 false。
  • 用 ?XDEBUG_TRIGGER=1 触发（trigger 模式，端口 9003）。

6核心要点

  • 经典主题 = PHP 造文档；块主题 = 核心画布解释块文本。 分叉点是 block-template.php:65 的 current_theme_supports('block-templates')。
  • 同一个菜单存在两套不兼容的模型： nav_menu（经典）和 wp_navigation（块）。换主题就是切换哪套模型生效。
  • core/post-content 只读 post_content 并跑 the_content —— 它不关心标记是谁生成的。
  • Elementor 在优先级 9 通过 the_content 发布编译 HTML，丢弃之前的过滤器产出 → 没有块、没有块锚点、Block Hooks 空操作；本轮链里 wpautop/texturize/shortcode_unautop 被摘掉。
  • 「保存了但没变化」= 数据源找错了，不一定是缓存。先查屏幕上那段标记来自哪一层。

7面试怎么考（对应题库）

Q1：「What's the difference between classic and block themes? Which would you recommend for a client project?」（题库 q47）

答法骨架：经典 = PHP 模板拼骨架 + Customizer/菜单/小部件三件套；块主题 = 块标记 + 站点编辑器 + theme.json；共同点 = 两条路都汇进同一条 the_content 流水线（所以插件与主题无关）。选型看谁维护：新站 + 客户自助 → 块主题；老站重度 PHP 定制 / Elementor 依赖 → 留经典（迁移会丢页头页脚侧边栏）；客户雇人写逻辑 → 经典更可控。

Q2：「Do Block Hooks work on Elementor pages? How would you make it work?」（题库 q49）

答法骨架：不行 —— Elementor 布局存在 _elementor_data，渲染时绕开块树，没有锚点；即使优先级 8 注入了标记，9 处被整体替换掉。兜底：the_content 优先级 999 + render_block() 手动渲染自己的块成 HTML 追加；代价 = 失去块级定位精度（只能首尾）。检测：_elementor_edit_mode meta 或 elementor/frontend/the_content 过滤器。

Q3：「A client says they saved a change but the page didn't update. Walk me through it.」

答法骨架：第一问「改的是渲染路径真正读的数据吗」——Elementor 页面读 _elementor_data、菜单读 nav_menu，改错数据源保存成功也没用；第二问缓存（页面缓存/CDN/对象缓存）；第三问模板层级有没有指向另一个文件。

Q4：「How does a block theme render a page header?」

答法骨架：template-canvas 取模板文本 → template-part 引用 parts/header.html → pattern 引用 → 真正的块（group + site-title + navigation）；wp:navigation 没有 ref 时会自动建 wp_navigation 文章。

满分心法：「Elementor 把 the_content 整个换掉」这一条能说出优先级 9 + 摘掉三个排版钩子，就已经超过绝大多数候选人 —— 他们只知道「Elementor 不能用 Block Hooks」这个结论，说不出机制。
