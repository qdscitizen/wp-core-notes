WP Super Cache Internals — How Page Caching Actually Works

Two-phase architecture · guard checks · dual file layers · mutex locking · the needs-rebuild rebuild window — read straight from the plugin source.

Study date: 2026-11-13  ·  Source: WP Super Cache on a local XAMPP install · WordPress 7.0.2
Reading scope: advanced-cache.php (all 29 lines) · wp-cache-phase1.php (all 195 lines) · wp-cache-phase2.php (4,014 lines — 4 sections, ~250 lines deep-read)

0TL;DR

Read early, write late. Phase 1 — included before WordPress boots — tries to serve a cached file and exits on a hit: WordPress never starts. On a miss, WordPress loads normally, and phase 2 captures the rendered HTML and writes it to disk for the next request.

One-liner: "Phase 1 serves on a hit and exits before WordPress boots; phase 2 captures the rendered page on a miss and writes the cache file. Read early, write late."

Extra exclusions in the supercache branch (L201-216): non-empty GET args / any cookie / Accept header not text/html / expiry check (L213: filemtime + $cache_max_time < time()) — any hit means don't serve.

On a hit: file_get_contents reads the HTML → (optional gzip) → output → exit. At that moment mu-plugins, plugins, the theme and the MySQL connection — none of them exist. That's the source-level proof of "a page-cache hit means WordPress never boots."

Late init — delaying serve until init (wp_super_cache_late_init)

The hit path above is the default mode: phase 1 tries to serve immediately — at that point WordPress has only loaded core files; no plugins, no theme. The Late init switch in the advanced settings (wp_super_cache_late_init) changes this: phase 1 L193 no longer serves immediately — instead, postload (L434-440) registers add_action('init', 'wp_cache_late_loader', 9999), so the serve-or-capture decision happens only after WordPress has fully loaded (after the init hook has fired).

DimensionDefault (early serve)Late init
Serve timingEarliest possible — plugins and theme not loadedAfter init — all plugins and theme functions.php loaded
Hit speedNear-instant (milliseconds, almost zero boot cost)Slower (pays the full WordPress bootstrap, tens to hundreds of ms)
Context correctnessPlugins never participate — a Chinese visitor may be served a cached English pageMultilingual / membership / device-detection plugins run first; the serve decision is context-correct
Cache key granularityURL onlyCan include locale, user group and other context dimensions — finer cache files
Best forPure content sites, simple blogsMultilingual (WPML/Polylang), membership sites, complex plugin ecosystems

When to use it: multilingual sites are the classic case — WPML/Polylang determine the locale only around init, so early serve can hand an English cached page to a Chinese visitor. Membership sites are the same: whenever personal context affects cache correctness, turn it on.

Benefit: the serve/cache decision is based on the fully-loaded WordPress context — maximum correctness; cache keys can include locale/user-group dimensions, so different visitor segments hit their own cache files.

Cost: even a cache hit now pays the full WordPress bootstrap (all mu-plugins, plugins, theme functions.php loaded) — the caching benefit is heavily reduced; hits degrade from milliseconds to hundreds of milliseconds. On a simple content site it's pure loss.

Interview line: "If late init is enabled, serving is delayed until the init hook — plugins like WPML get to run first, so the cache decision is context-correct. The trade-off: even a cache hit pays for the full WordPress bootstrap. Simple sites keep it off; multilingual or membership sites turn it on for correctness."

4Phase 2 — the write side (what happens on a miss)

  1. Phase 1 misses (no cache file, or expired) → WordPress boots normally
  2. mu-plugins → plugins load → wp-settings.php:614-616:
    if ( WP_CACHE && function_exists('wp_cache_postload') ) wp_cache_postload();
    — a slot core reserves specifically for page-caching plugins
  3. wp_cache_postload() (L418) → wp_cache_phase2() → L1913: ob_start('wp_cache_ob_callback') — the buffer is attached and every byte of rendered HTML flows into it
  4. Rendering finishes, the buffer closes → wp_cache_ob_callback($buffer) (L2394) runs the validation chain: fatal error / DONOTCACHEPAGE / POST / preview / REST / redirect / 304 / per-page-type settings / unknown page type / logged-in users
  5. Everything passes → L2495 calls wp_cache_shutdown_callback() to write to disk: supercache directory + meta JSON
  6. The next request goes back to step 1 → hit → served on the earliest path
The two validation chains are not duplicates — they're layered. Phase 1 answers "may I serve?" (WordPress isn't loaded yet; only superglobals are available). Phase 2 answers "may I cache?" (WP_Query is ready, so exclusions can be precise: is_single, is_page, is_search).

5The moment a cache expires — three branches (htaccess / PHP / GC)

An anonymous visitor requests an expired cached page. What they see depends on configuration:

BranchConditionWhat the visitor gets
① htaccess / Expert modemod_rewrite rules only check "file exists", not expiryThe stale old page — until the scheduled GC deletes expired files (a known Expert-mode trait: serve stale until GC)

③ GC already ranScheduled cleanup (wp-cron / schedule_wp_gc, L1927) already deleted the expired fileFile missing → miss → re-render → new cache → new page
These three branches explain the "sometimes visitors see an old page, sometimes a new one" mystery: it depends on the site's cache mode (Expert vs PHP) and whether the GC has run. The performance/freshness trade-off lives in that mode choice.

6Concurrent writes — the mutex

Phase 1 L49-50 defines $mutex_filename = 'wp_cache_mutex.lock'. Why a lock is needed: two requests writing the same cache file means a later visitor can read a half-written HTML file — a broken page. The lock guarantees a single writer:

The first request to grab the lock → renders + writes the cache file + releases
Concurrent requests               → render their own pages normally, just don't write
→ nobody ever reads a half-written file

Source Easter egg: the L48 comment reads "this coarse file locking should really be removed" — the author admits it's a coarse global lock (one lock file for every page), serializing cache writes under high concurrency. Historical reason: some hosts didn't support semaphores back in the day. Knowing "the author himself wants it gone" is proof you actually read it.

7Dogpile / thundering herd — needs-rebuild and the 10-second guard

Scenario: a hot page's cache expires with 100 visitors/sec arriving. The first request triggers a rebuild that takes a few hundred milliseconds — what do those 100 visitors experience?

Answer (wpcache_do_rebuild, phase2 L1972; source comment quoted verbatim): the plugin doesn't delete the expired file — it renames it to index.html.needs-rebuild and rebuilds in the background:

// if the file is index.html.needs-rebuild and index.html doesn't exist and
// if the rebuild file is less than 10 seconds old then remove the ".needs-rebuild"
// extension so index.html can be served to other visitors temporarily
// until index.html is generated again at the end of this page.

Interview script (the dogpile answer — memorize this): "When a cached file expires, WP Super Cache doesn't delete it — it renames it with a .needs-rebuild suffix and rebuilds in the background. While rebuilding, other visitors can still be served the old file — the plugin restores the extension as long as the rebuild marker is less than 10 seconds old, so there's no empty window. And if the rebuild crashes, the 10-second guard stops the stale file from being resurrected forever."

8Interview log — main question + three follow-ups (2026-11-13 live session)

Main: "How does full page caching work internally?"

Answer structure: drop-in mount (wp-settings.php:102) → guard checks (admin / cookies / POST) → serve_cache_file hit decision → serve and exit (WordPress never boots) → on a miss, postload → ob_start capture → validation chain → write file. The dual file layers must be mentioned.

Follow-up 1: "Why two file types?"

Core: can the file be located from the URL alone? supercache is pure static with a URL-mapped path → nginx/Apache serves it directly at image-level performance; wp-cache carries meta → must enter PHP to read JSON and decide the response. The safety premise: anonymous content is identical for everyone and can be shared; a cookie means personalization — never share static files.

Follow-up 2: "Two visitors hit the same uncached URL at the same second — what happens?"

Core: the mutex. The first to grab it renders and writes; concurrent requests render normally without writing — nobody reads a half-written file. Easter egg: the source comment admits the coarse lock "should really be removed" (old hosts lacked semaphore support).

Follow-up 3: "Cache expired, 100 visitors/sec — what do they see during rebuild?"

Core: the expired file isn't deleted — renamed with .needs-rebuild while rebuilding in the background; during the window visitors are served the restored old page (stale but complete, no empty window); the 10-second guard prevents a crashed rebuild from resurrecting the stale file forever.

The winning pattern: the main question shows the two-phase architecture and dual files; follow-ups drill deeper — locking, dogpile, status codes, mode differences. Every answer traces back to source lines, not concept recitals.

9Scenario chains — four drills (main question + three follow-ups each)

Interviewers rarely ask "how does page caching work" cold. They wrap it in a client scenario and drill. Four chains below cover the real surface: layered diagnosis, personalization, WooCommerce, and the POST disaster.

Chain A — "The invisible redesign" (layered diagnosis)

Main: "A client published a new homepage design hours ago. Some visitors still see the old one. Walk me through your diagnosis."

FU1 — How do you find out WHICH layer is caching? Peel from outside in: hard refresh (browser), then check CDN response headers (Age, X-Cache) with curl, then temporarily disable the page cache, then the object cache. Don't guess — each layer has a header or a switch.

FU2 — It's the page cache. How do you purge it right now? The plugin's purge button, wp-cli, or simply re-saving the page — save_post fires the purge automatically. If a CDN sits in front, purge its API too.

FU3 — How do you prevent this next time? Purge-on-publish should already be automatic (hooks); if a CDN is involved, wire its purge API into publishing too — and set the client's expectation about propagation delay.

Insider signal: peeling layers outside-in using headers, not guessing "clear the cache and pray."

Chain B — "Members seeing each other's data" (personalization)

Main: "On a membership site with page caching, members occasionally see ANOTHER member's name or cart contents. What went wrong?"

FU1 — Root cause? A personalized page got cached and re-served to someone else. Either the cache plugin doesn't recognize the membership plugin's cookie (it only knows wordpress_logged_in_), or an exclusion for member pages is missing.

FU2 — Fix options? Three: exclude member URLs from the cache; cache the static shell and load personalized parts via AJAX; add the membership cookie to the rejected-cookie list so those requests never hit the cache.

FU3 — How do you verify the fix? Two browser profiles — one logged in, one anonymous — load the same page and compare. Plus check response headers for cache-hit indicators on every variant.

Insider signal: the shell + AJAX pattern for personalization, and testing with two parallel sessions.

Chain C — "Caching a WooCommerce store" (commerce)

Main: "How would you set up page caching for a WooCommerce store with 5,000 products?"

FU1 — Which pages must never be cached? Cart, checkout, my-account — and anything reached by POST. These are personal and state-changing; the cache plugin's cart-cookie detection usually handles them, but verify the exclusions explicitly.

FU2 — Product pages: cacheable? What happens when a price changes? Cacheable — product pages are identical for anonymous visitors. When a price changes, WooCommerce fires hooks on save, and the cache plugin purges that product's cache (the lookup table updates in the same save). Stale prices mean the purge wiring is broken.

FU3 — Does caching break "Only 3 left in stock" badges? It can go stale for the cache duration. Either accept a few minutes of imprecision, refresh stock via JS, or exclude product pages if stock precision is business-critical.

Insider signal: knowing WooCommerce fires purge hooks on product save, and that the cart cookie is the line between cacheable and not.

Chain D — "The confirmation page leak" (the POST disaster)

Main: "After enabling a page cache, some visitors received OTHER people's form submission confirmation pages. What happened?"

FU1 — Root cause? A confirmation page was cached and re-served. Two usual suspects: the form submits via GET (query-string URLs got cached), or an intermediate layer — typically a CDN — cached the POST response.

FU2 — Which layer is guilty? Page-cache plugins refuse POST requests (the guard chain checks the request method), so the plugin itself is rarely the culprit. Check the form method first; if it's POST with a confirmation leak, the CDN is the usual suspect.

FU3 — Hardening? Cache-Control: no-store on confirmation endpoints, POST-only forms, and tokenized one-time confirmation URLs so a cached copy is useless to anyone else.

Insider signal: suspecting the CDN instead of blaming the page cache — because you know the plugin's guard chain refuses POST.

Why these four: layered diagnosis (operations), personalization (membership), commerce rules (WooCommerce), and the POST disaster (safety). Between them they touch every guard check in the source — without quoting a single line number.

10Key takeaways

  • Read early, write late: phase 1 (wp-settings.php:102) serves and exits; phase 2 (:614 → postload → ob_start) captures and writes.
  • Dual file layers: supercache pure static can bypass PHP entirely (Expert mode); wp-cache carries meta and is served through PHP.
  • Two validation chains, layered: phase 1 answers "may I serve", phase 2 answers "may I cache"; DONOTCACHEPAGE is respected by both.
  • Expiry is not a timer: PHP mode checks on read (mtime + max_time); Expert mode may serve stale until GC runs.
  • Concurrency and herds: the mutex prevents half-written files; needs-rebuild + the 10-second guard prevents the dogpile empty window.
