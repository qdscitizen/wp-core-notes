9Scenario chains — four drills (main question + three follow-ups each)

Chain A — "The voting plugin went viral — and the whole site slowed down"

Main: "Traffic to our helpful-vote plugin grew, and now the entire site is slow. Why would a voting feature drag down everything?"

FU1 — The mechanism? Every vote is one update_post_meta → the last_changed version bumps → every WP_Query cache entry site-wide goes stale. More votes per second, shorter average cache lifetime.

FU2 — Didn't Redis fix this? It made it visible: Redis shares the list cache across visitors — its whole value is "visitor B hits visitor A's query". With the version bumping constantly, that shared cache keeps getting invalidated. The expensive component is doing nothing.

FU3 — Fix and timing? Move counts to a dedicated table — its writes never touch the posts version number. The timing rule: "post meta now, custom table when querying becomes a feature" — or when vote frequency demonstrably thrashes the cache, or when a ranked list ships.

Chain B — "Pages are slow for logged-in users but instant for anonymous visitors"

Main: "Editors and members complain the site is slow, yet anonymous visitors get lightning-fast pages. Why?"

FU1 — Why does page caching skip logged-in users? Page cache stores finished HTML — which carries a personal point of view (login bar, cart, greeting). Serving visitor A's finished page to visitor B is data leakage. So the plugin sees the login cookie and skips: logged-in users get their pages built every time.

FU2 — How does Redis help? Building a page is two steps: query data (expensive) + assemble HTML (cheap). Page caching skips BOTH steps; object cache skips only the querying — and data has no owner, so logged-in users' queries hit Redis. Pages drop from hundreds of ms to tens.

FU3 — What's the production standard? Both layers stacked: page cache serves anonymous visitors at maximum speed, object cache serves logged-in users and cache misses as the fallback.

Chain C — "Ops updated the database directly — the front end shows the old value forever"

Main: "Ops changed a meta value with raw SQL, confirmed it's new in the database — but refreshing the front end a hundred times still shows the old value. Why?"

FU1 — Why doesn't refreshing help? Reads are cache-first: get_post_meta asks Redis, the old entry is still alive (nobody deleted it), it returns immediately. The new value sits in the database and never gets read.

FU2 — The fix? Raw SQL bypassed the hooks — no cache delete, no version bump. Remedy: call clean_post_cache($post_id) — it deletes the per-post entry and bumps the version in one call.

FU3 — How do you prevent a repeat? Policy: all writes through the standard API; when raw SQL is unavoidable, code review checks for clean_post_cache after the write. The interview value is the three-layer story: fresh database / stale cache / cache-first read order.

Chain D — "What do transients have to do with the object cache?"

Main: "Where does set_transient() actually store data — and why did transient operations get faster after we installed Redis?"

FU1 — Where does it live without Redis? In the wp_options table — that's why transients are cross-request even without persistent caching (the database is the fallback), but every read is a database query.

FU2 — After installing Redis? Once object-cache.php takes over, transients move into Redis memory — reads go from database queries to microsecond memory operations. Plugins that lean on transients (WooCommerce, SEO suites) speed up wholesale.

FU3 — How does expiry differ? Transients use explicit TTLs (the third argument — time-driven). The object cache itself is event-driven (data changes → invalidate immediately; unchanged → lives on). Two different philosophies.

Insider signals: A — the mechanism "high-frequency version bumps invalidate the shared cache"; B — "Redis saves the querying, not the assembly"; C — the three-layer narrative (fresh DB / stale cache / cache-first reads); D — separating time-driven from event-driven. Four chains, zero line numbers, all mechanism.

WP Object Cache — Invalidation, Redis & Interview Notes

Meta cache vs query cache · last_changed version numbers · Redis & object-cache.php — verified against WordPress 7.0.2 source (file:line evidence)

0TL;DR

One meta write touches two different caches: it deletes that post's meta cache entry, and it bumps a site-wide version number used by every query cache. The first is cheap to rebuild (one indexed row). The second is expensive to rebuild (a full list query).

wp_postmeta table
├── meta cache (group: post_meta, key = post_id) → invalidated by precise delete
└── query cache (group: post-queries, key = query args) → invalidated by version number

1What happens the moment you call update_post_meta

One line of code does three things:

// What you write:
update_post_meta( $post_id, 'count', 5 );

// What actually happens:
1. UPDATE wp_postmeta ...                      // what you wanted
2. wp_cache_delete( $post_id, 'post_meta' )    // delete this post's meta cache
3. Fires updated_post_meta hook
   → wp_cache_set_posts_last_changed()
   → wp_cache_set_last_changed( 'posts' )      // bump the version number

Source: wp-includes/meta.php:329, wp-includes/post.php:8410

2Two caches, two invalidation paths

Meta cacheQuery cache

Common misconception: "if last_changed changed, get_post_meta must re-query too." Wrong — get_post_meta never reads last_changed. It only checks whether its own per-post meta cache entry was deleted.

3How WP_Query knows its cache is stale (salted cache, WP 6.9+)

Since 6.9 WordPress uses a "salted cache": the key stays stable, the version number is stored inside the cached value, and it is compared on read.

// On write: the version is stored inside the entry
wp_cache_set_salted( $key, $data, 'post-queries', $last_changed );
// → stored as: { data: [...], salt: "1700000000" }

// On read: version mismatch = treated as a miss
wp_cache_get_salted( $key, 'post-queries', $last_changed );
if ( $salt !== $cache['salt'] ) return false;
// → miss → run the SQL → store again with the new version

Source: wp-includes/cache-compat.php:214 / 244 (@since 6.9.0)

Key point: the cache entry is not deleted — it is still sitting in Redis. It is simply ignored on read because its "version stamp" no longer matches. Think of a stale check in React Query.

Before 6.9, the version was hashed into the key instead — every bump created a new key and orphaned the old one. 6.9 switched to a stable key with version comparison, so Redis doesn't accumulate zombie keys.

4Why list queries are expensive to rebuild

// Single meta: hits the (post_id, meta_key) index, one row
SELECT meta_value FROM wp_postmeta
WHERE post_id = 123 AND meta_key = 'count';

// List query: multiple joins + sorting + pagination + a count query
SELECT wp_posts.* FROM wp_posts
  LEFT JOIN wp_term_relationships ...
  LEFT JOIN wp_term_taxonomy ...
WHERE post_type = 'post' AND post_status = 'publish'
ORDER BY post_date DESC LIMIT 10 OFFSET 0;
// plus a separate COUNT(*) for the total page count

Frontend analogy: byId[123].count (O(1)) versus all.filter().sort().slice() (O(n log n)).

Interview line: "post meta now, custom table when querying becomes a feature." Don't say "I'd just write raw SQL to bypass the hooks" — that works around the problem; migrating solves it.

6What Redis and object-cache.php actually are

Default: the object cache lives for one request

WordPress ships with an in-process object cache (a PHP array inside WP_Object_Cache). When the request ends, the array is destroyed — nothing is shared between visitors. So by default, query caches only serve repeated queries within the same request.

What Redis changes

Drop a file at wp-content/object-cache.php (a drop-in). WordPress loads it early during bootstrap, and it takes over every wp_cache_* function — moving the cache from process memory to a Redis server.

Defaultobject-cache.php + Redis
StoragePHP memory arrayRedis server
Cross-request❌ destroyed with the request✅ shared by all visitors
List cache valueAlmost noneVisitor A warms it, visitor B hits it
The three drop-ins: object-cache.php (object cache), advanced-cache.php (page cache), db.php (database layer). All load before regular plugins.
Key consequence: the "votes thrash the list cache" problem is only serious on sites with Redis — because the cache is shared across requests. Without Redis, the cache never outlives a request, so invalidation costs nothing.

8How this is tested in interviews

HIGH1. "How does WordPress keep the object cache fresh after content changes?"

"Meta writes fire hooks like updated_post_meta, and core updates a last_changed timestamp in the posts cache group. WP_Query uses that timestamp — since 6.9 it is stored as a salt inside the cache entry and compared on read — so every old query cache entry becomes stale at once. It's a version number instead of deleting entries one by one. The per-post meta cache is separate: it's deleted precisely by post ID."

HIGH2. "Why do I see stale data after updating meta directly in the database?"

"Because the standard API wasn't used — raw SQL doesn't fire the meta hooks. The per-post meta cache wasn't deleted and last_changed wasn't bumped, so both caches keep serving old data. The fix is to call clean_post_cache( $post_id ) after the raw query."

MID3. "A post goes viral and the whole site slows down — why?"

"Every vote calls update_post_meta, which bumps the last_changed version, so every query cache entry on the site goes stale at once. On a site with Redis the shared list cache keeps getting invalidated and the database gets hit repeatedly. For high-frequency counters I'd move them to a dedicated table so writes don't touch the posts cache group." — this answer is the differentiator level.

MID4. "What's the difference between page cache and object cache?"

"Page cache stores the finished HTML and serves it before PHP boots — it lives in the advanced-cache.php drop-in. Object cache stores query results and data inside PHP, so the page is still assembled each time, but the database isn't hit. With Redis the object cache is shared across requests; without it, it only lives for one request."

DEEP5. "What are drop-ins?"

"Special files in wp-content that load before regular plugins — object-cache.php for Redis, advanced-cache.php for page caching, db.php for the database layer."

The winning point: these questions are not about memorizing parameters — they test whether you know that two invalidation paths run side by side: precise deletes (single objects) and version numbers (query results). Most candidates only know one. The moment you say "get_post_meta never reads last_changed," the interviewer knows you've read core.
