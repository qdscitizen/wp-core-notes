02Block Hooks API（wpex-helpful-block V0.1 已发布）

能上线的规则：

{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "wpex/helpful",
  "blockHooks": {
    "core/post-content": "lastChild"   // camelCase —— 见下面的坑
  }
}

通过 register_block_type_from_metadata() + render_callback 注册。块自动追加到每篇文章 —— 零配置，经典主题和块主题都生效（两条路径都汇进同一条 the_content 链）。

03安全 —— 四道门（投票端点已发布）

请求生命周期每个环节一道门，每道门拦一种攻击：

生命周期门拦什么攻击
发出请求nonce（X-WP-Nonce 头）CSRF —— 伪造提交
到达端点前permission_callback → current_user_can()越权
输入absint()（数字）/ sanitize_text_field()（文本）/ kses（富文本）脏数据与注入输入
写库$wpdb->prepare()SQL 注入
输出esc_html() / esc_attr()XSS
加分细节：公开操作（匿名投票）用 __return_true + nonce；管理操作要求 capability 检查 —— 门的强度跟着操作性质走。字段类型选清洗函数：数字用 absint、文本用 sanitize_text_field —— 三种守卫三条路，绝不混用。

实测证据 —— SHOW INDEX FROM wp_postmeta（12,670 行）：PRIMARY (meta_id) · post_id 有索引 · meta_key 有索引（191）· meta_value 无索引（LONGTEXT）

04wpautop —— 被源码纠正的一次

blocks.php L2528–2552

规则：空行 → <p>，单换行 → <br>。（不是 "beatify" —— 是 beautify。这个错拼第三次出现了，已进永久错题本。）

内容里含块时，do_blocks 到底干了什么

// blocks.php L2526–2529 —— do_blocks() 内部：
if ( false !== $priority && doing_filter('the_content') && has_blocks($content) ) {
    remove_filter('the_content', 'wpautop', $priority);
    add_filter('the_content', '_restore_wpautop_hook', $priority + 1);
}
// L2545 —— 恢复钩子：
function _restore_wpautop_hook( $content ) {
    add_filter('the_content', 'wpautop', $current_priority - 1);   // 放回 10 —— 但本轮已经过了
    remove_filter('the_content', '_restore_wpautop_hook', $current_priority);
    return $content;   // 原样返回 —— 它只负责恢复链状态
}
一次由学习者发起、用源码推翻 AI 的纠正：我（AI）最初教「动态块输出必须紧凑，否则会被 wpautop 破坏」。学习者打开 blocks.php 找到摘除/恢复逻辑，推翻了这个说法：内容含块时，wpautop 被整条摘出链外 —— 动态块输出天然免疫。输出紧缩短是卫生习惯，不是保命符；wpautop 的坑只存在于无块的经典内容里（经典编辑器文章、纯文本短码）。

05演进策略：现在用 meta，将来才迁表

一条命令读得快，另一条命令排序就慢：

操作索引路径速度
get_post_meta( 40, 'wpex_helpful_up' )WHERE post_id = 40 AND meta_key = '…' → 索引命中一行快 ✅（V0.1 只做这件事）
ORDER BY meta_value+0 DESC（做一个「最有用 Top 10」页）meta_value 是 LONGTEXT 无索引 → 读出全部再排序慢 ❌（触发迁表）
面试标准答案最终版："V0.1 用 post meta 是正确选择：计数是每篇文章自己的数据，我只按 post ID 读，走的是索引查找。只有当某个功能需要跨文章按票数查询或排序时，我才把计数迁进带正确索引的独立表。所以：post meta now, custom table when querying becomes a feature."

06WooCommerce 数据架构 —— 一次 save()，三张表

实测：DESCRIBE wp_wc_product_meta_lookup

$product->set_price( 99 );   // 只改内存 —— 数据库还不知道
$product->save();
├ ① wp_posts                  // 身份与主内容 —— 锚点
├ ② wp_postmeta               // 弹性属性（_price、_sku、插件数据）
└ ③ wp_wc_product_meta_lookup // 查询副本：min_price DECIMAL(19,4) + MUL 索引，stock_quantity + MUL…

设计上是两层：posts/meta 是内容层（真相来源 —— WP 生态兼容：WP_Query、REST、SEO 插件都读 posts）；lookup 表是查询层（反规范化副本：用一点写入开销换取带索引的筛选与排序）。前台价格筛选打的是 lookup.min_price —— 真正的 DECIMAL 列带索引，永远不打 LONGTEXT 的 meta_value。

前端镜像：主数据库 + 搜索索引。写一次，查询走索引副本。等我们的 helpful 块长出「最有用文章」页面时，官方 lookup 表的做法就是数据库里现成的参考实现。

07经典 vs 块主题 —— 两个主题目录对照读

TT5 激活 · Astra 旁读。同一个页面，两个物种（single 模板）：

// 经典（astra）：single.php —— PHP + HTML 混写
get_header();
<div id="primary"><?php astra_content_loop(); ?></div>   // 内部调用 the_content()
get_footer();

// 块（twentytwentyfive）：templates/single.html —— 纯块标记
<!-- wp:template-part {"slug":"header"} /-->
<!-- wp:post-title /-->
<!-- wp:post-content /-->        // ← 就是 the_content()，底下同一条流水线
<!-- wp:template-part {"slug":"footer"} /-->
经典块
模板形态PHP 文件带块标记的 HTML
改结构改代码站点编辑器拖块 → 文件自动更新
定制工具三件套：Customizer / 菜单 / 小部件站点编辑器 + theme.json 设计系统
内容渲染两条路都汇进 the_content 流水线 —— 插件与主题无关（已验证：helpful 块在两种主题下都渲染）
选型逻辑 —— 「之后谁维护」："新站 + 客户要自己改 → 块主题：站点编辑器就是为这个而生的。大型老站 → 留经典：迁移会丢页头、页脚、侧边栏，成本大于收益。要写重度定制逻辑且有开发者 → 经典更可控。"

09方法论 —— 用源码验证 AI

核心纪律：

案例 1 —— camelCase 陷阱

豆包建议 "core/post-content": "after"；Hermes 建议 "last_child"。两个都错。源码（blocks.php L719–724）：键是 lastChild。插件带着错误的写法上线 → 运行时诊断 → 靠源码修好。判定：源码 1 – 0 – 0。

案例 2 —— 一次「学习者纠正 AI」

Hermes 先教「动态块输出必须紧凑否则被 wpautop 破坏」，又批评学习者的 remove/restore 答案是错的。学习者打开 blocks.php 找到 L2528–2529，推翻了这个教法。修正后的判定：块内容对 wpautop 天然免疫；紧凑输出是卫生，不是铠甲。
