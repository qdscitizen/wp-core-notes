WordPress 内核机制 — 渲染路径、写入路径、安全与块系统

读路径、写路径、安全层与块系统 — 全部对照本地源码逐行核实（file:line 证据）。

学习窗口：2026 年 10–11 月  ·  本地环境：XAMPP（Apache :80，PHP 8.2.12，MySQL 5.7） ·  WordPress 7.0.2
方法：读源码拿 file:line 证据 → 浏览器实测 → Xdebug 断点验证行为

1the_content 读路径 — 一条单向流水线

前台渲染链注册在 wp-includes/default-filters.php:201–210，是严格的单向管道（像 Array.reduce，不是 addEventListener）。每个回调接收前一个回调的返回值；在优先级 20 追加的内容，永远不会再流回 8–11。

优先级回调实际做什么
8apply_block_hooks_to_content_from_post_object把插件声明的「钩子块」注入标记字符串（改树，还没生成 HTML）
9do_blocks解析块标记，对动态块执行 render_callback — 标记变成 HTML
10wptexturize · wpautop · shortcode_unautop · prepend_attachment · wp_replace_insecure_home_url排版（"→“，...→…，跳过 pre/code）、段落包装、清掉短码外壳的 <p>
11do_shortcode故意排在 wpautop 之后，让短码输出躲过段落包装
12wp_filter_content_tags图片 / iframe 懒加载、srcset
20convert_smilies文本表情 → GIF（最后跑，生成的 HTML 也会被排版）
同优先级下按注册顺序执行：remove 再 add wpautop（优先级 10）会悄悄把它排到 shortcode_unautop 后面 —— 写「条件 wpautop」时的真实陷阱。

2短码与钩子 API 内部

  • 成对短码（[foo]body[/foo]）把 $content = $m[5] 传给处理函数（shortcodes.php:432）。不递归 — 嵌套短码需要处理函数自己调 do_shortcode($content)。
  • has_shortcode() 在内容不含 [ 时直接短路返回，不解析；含括号时再验证注册、递归内层（shortcodes.php:149–169）。
  • remove_filter() 只从 WP_Hook->callbacks[$priority] 删掉一个回调键；WP_Hook 对象本身复用，不重建（plugin.php:124–126）。
  • make_clickable()（URL 转 <a>）默认不在 the_content 链上。
插件里常见的 remove_filter('the_content','wpautop') 之所以存在：wpautop 在优先级 10 已经跑过，而你的回调也是 10 —— 只能先摘掉再重新挂，才能控制顺序。

3块 — 静态 vs 动态，配置放在哪

静态块 — core/paragraph

// wp-includes/blocks/paragraph.php:45
function register_block_core_paragraph() {
    register_block_type_from_metadata(
        __DIR__ . '/paragraph'   // 没有 render_callback
    );
}
add_action( 'init', 'register_block_core_paragraph' );

服务端原样输出存储的 HTML；只有 render_block_core/paragraph 这类过滤器会碰它（比如自动补 wp-block-paragraph 类名）。

动态块 — core/accordion

// wp-includes/blocks/accordion.php:41
register_block_type_from_metadata(
    __DIR__ . '/accordion',
    array(
      'render_callback' =>
        'render_block_core_accordion',
    )
);

do_blocks → WP_Block::render() 执行回调（class-wp-block.php:596）。没注册的块标记不算动态 —— 它内部的 HTML 照样打印。

配置文件地图

文件作用
wp-includes/blocks/<name>/block.json单个块的清单：name、attributes、supports + editor.css/style.css
wp-includes/blocks/<name>.php动态块的 render_callback，由 blocks/require-dynamic-blocks.php 加载

Block Hooks（优先级 8）— 「自动把我挂上去」

插件在 block.json 声明 "blockHooks": { "core/post-content": "after" }；apply_block_hooks_to_content_from_post_object()（blocks.php:1214）把文章包进临时容器块，在它后面插入 <!-- wp:myplugin/note /-->，再解开。优先级 8 排在 do_blocks 之前，正是为了让注入的标记有机会在 9 被渲染。

Gutenberg 只是历史项目名；代码里只有 core/paragraph 这种块名。「Gutenberg 块」= 块。

4pre_* 写路径 — INSERT 之前的输入清洗

这些钩子只在官方写函数运行时触发（上下文 'db'），读操作永远不触发：

操作入口函数过滤器应用位置
插入 / 更新文章wp_insert_post() → sanitize_post($postarr,'db')post.php:4539 → :3118
插入 / 更新分类项wp_insert_term() / wp_update_term()taxonomy.php:2477 / :3255
创建 / 更新用户wp_insert_user()（逐字段手写清洗）user.php:2376–2490
提交评论wp_new_comment() → wp_filter_comment()comment.php:2220, :2228
直接 $wpdb->insert()—任何 pre_* 都不跑

短字符串的三段式管道（default-filters.php:32–35）

  1. sanitize_text_field — 检查非法 UTF-8、剥标签（script/style 整块消灭）、压缩 [\r\n\t ]+、去首尾空白、移除所有 %xx 编码（formatting.php:5633）
  2. wp_filter_kses — 用窄名单 $allowedtags 的白名单过滤（kses.php:602）；文章正文用的是宽得多的 $allowedposttags
  3. _wp_specialchars（优先级 30）— & < > 转实体，引号不动，不重复编码
每个字段都是一对：pre_term_name（存）vs term_name（显示，admin 侧二次加固）。写入时清洗，读取时纵深防御。

5Nonce — 证明意图，不是权限

nonce 回答「是不是当前用户自己的浏览器主动发的？」，current_user_can() 回答「这个用户有没有资格做？」。Cookie 会随跨站请求自动带上，所以只有权限检查挡不住 CSRF。两个都要，nonce 在前。

场景生成校验
后台表单wp_nonce_field($action) functions.php:1899check_admin_referer() pluggable.php:1372
链接动作wp_nonce_url() functions.php:1868同上
AJAXlocalize 传 noncecheck_ajax_referer() pluggable.php:1417
REST + cookie 认证wp_create_nonce('wp_rest') → X-WP-Nonce 头rest_cookie_check_errors() rest-api.php:1122
  • cookie 认证的 REST 请求缺 nonce → wp_set_current_user(0)，请求静默变成游客（rest-api.php:1150）— 症状是误导性的 403「forbidden」。
  • 哈希输入 = tick | action | uid | session_token（pluggable.php:2533）：登出、换会话、换 action 都立即失效。
  • 有效期 24 小时，分两个 12 小时窗口 —— wp_verify_nonce 返回 1（当前窗口）或 2（上一窗口）（:2486–2500）。
  • 核心在成功响应里回一个新的 X-WP-Nonce 头（rest-api.php:1162）；从不读它的客户端 24 小时后开始全线失败。
DraftLab Pro 插件审计发现：后台 JS 只在页面加载时取一次 nonce，从不从响应头刷新 —— 后台标签页开着超过 24 小时就开始 403，必须刷新页面。修复：每次请求后读响应头 X-WP-Nonce 更新本地值。

6案例研究：「为什么两个顶部导航项删不掉？」

Happy Paws 演示站 = 块主题（Twenty Twenty-Five）+ Elementor 搭的首页。这一个事实解释了所有死胡同：

站点编辑器「导航」（wp_navigation #4）实际显示的顶部导航（经典菜单 #59）
存储一行 wp_posts，内容是块标记 <!-- wp:page-list /-->wp_terms term + nav_menu_item 文章 + wp_postmeta + wp_term_relationships
渲染者主题 patterns/header.php 的 wp:navigation 块（自动创建，回退成页面列表）Elementor 的「WordPress Menu」小部件（Unlimited Elements），绑定到该菜单
在哪编辑站点编辑器 → 导航外观 → 菜单 —— 不可见，因为块主题不注册菜单位置

为什么改站点编辑器的导航没用： 两套并行的导航系统，数据零关联。块主题的导航只渲染在 Elementor 没接管的模板上（404、归档页）。

可行的删除路径

  • 借经典主题的后台界面： 切到 Astra（它会注册菜单位置，astra/inc/admin-functions.php:28）→ 外观 → 菜单重新出现 → 删项 → 切回。菜单数据与主题无关。
  • 直接改数据库（菜单项 ID 9692、9700）：删 wp_postmeta → wp_term_relationships → wp_posts WHERE post_type='nav_menu_item'，三张表，不是一张。
直接改库只在「值自包含」时可行（菜单项、文章字段）。绝不要手改序列化的 option 值（长度前缀会破坏 unserialize）、密码哈希或反规范化的计数器。

7工具 — XAMPP 下的 Xdebug

  • 安装： php_xdebug-3.4.0-8.2-vs16-x86_64.dll 放进 D:\xampp\php\ext\；php.ini 加 zend_extension、xdebug.mode=debug、xdebug.start_with_request=trigger、端口 9003。
  • trigger 模式优于常开： 没有监听器时每次页面加载都会卡几秒。只在带 ?XDEBUG_TRIGGER=1（或浏览器助手扩展 / cookie）时才启动调试。
  • VS Code： PHP Debug（felixfbecker）扩展，配置「Listen for Xdebug」，端口 9003，本地无需 pathMappings。
  • 断点要打在正确的执行路径上： do_blocks 只在前台渲染（the_content）命中，后台编辑页不命中 —— 后台 REST context=edit 返回的是原始存储内容。
在 do_blocks() 里看着 $content 从 <!-- wp:paragraph -->… 标记变成最终 HTML —— 是吃透整条块流水线最快的方式。

8核心要点

  • 读路径 vs 写路径： the_content 每次渲染都跑；pre_* 每次保存只跑一次。两条管道，两套心智模型。
  • 块 = 有名字、有参数的组件。 注册 = 元数据 + 可选 render_callback；回调存在与否，就是静态/动态的全部区别。
  • 所有「看得见但 grep 不到」的东西都在 MySQL 里： 菜单、小部件、选项、Elementor 数据。怀疑 grep 之前，先搜数据库。
  • 块主题 ≠ 没有菜单： 它只是隐藏了经典菜单界面。数据和消费方（Elementor、插件）照常工作。
  • nonce ≠ capability；trigger 模式的 Xdebug ≠ Xdebug 坏了。 两个「故障」其实都是正确行为，在等正确的调用方式。

9面试怎么考（对应题库）

Q1：「Explain what happens to post content between the database and the browser.」（题库 q46）

答法骨架：模板调用 the_content() → 触发过滤链 → 8 注入钩子块 → 9 do_blocks 解析块（有块时 wpautop 被摘掉，之后通过 restore hook 放回）→ 10 排版/段落 → 11 短码 → 12 懒加载 → 浏览器。要点：单向管道，追加在后面的内容不会回流。

Q2：「What is wpautop and when does it break plugin output?」（题库 q50）

答法骨架：空行转 <p>、单换行转 <br>；坑只在无块经典内容（div 被拆开包 p）；块上下文里 do_blocks 会把它从链上摘掉 → 块输出天然免疫；同优先级顺序陷阱：remove+re-add 会挪位置。

Q3：「How do you add a custom block that renders on the server?」（对应第 3 节）

答法骨架：block.json（name/attributes/supports）+ register_block_type_from_metadata + render_callback；do_blocks → WP_Block::render() 执行回调；静态块没有回调，输出存储的 HTML。

Q4：「Where does WordPress sanitize input, and what if I use $wpdb directly?」（对应第 4 节，题库 q48）

答法骨架：pre_* 只在官方写函数里跑（wp_insert_post / wp_insert_term / wp_insert_user / wp_new_comment）；$wpdb->insert() 一个都不跑 → 自己 sanitize + prepare；短字符串三段：sanitize_text_field → wp_filter_kses → _wp_specialchars。

Q5：「Nonce vs capability — why do you need both?」（对应第 5 节，题库 q48）

答法骨架：nonce = 意图（是不是你自己浏览器主动发的），capability = 资格（你有没有权做）；cookie 会随跨站请求带上，所以只有 capability 挡不住 CSRF；REST 缺 nonce 会静默变游客（403 假象）；nonce 24 小时过期，客户端要从 X-WP-Nonce 响应头刷新。

满分心法：这组题的分不在名词解释，在能报出源码位置 + 说出「为什么这样设计」。比如「为什么 Block Hooks 放优先级 8」——因为要赶在 do_blocks(9) 之前把标记塞进去。
