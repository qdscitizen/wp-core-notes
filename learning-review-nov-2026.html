01The the_content Pipeline wp-includes/default-filters.php L201–210

02Block Hooks API shipped in wpex-helpful-block V0.1

The rule that ships

{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "wpex/helpful",
  "blockHooks": { "core/post-content": "lastChild" }  // camelCase — see the trap below
}

Registered via register_block_type_from_metadata() + a render_callback. The block auto-appends to every post — zero configuration, works under classic and block themes (both paths run through the same the_content chain).

Position mapping — the silent trap (blocks.php L719–740)

$position_mappings = array(
    'before'     => 'before',
    'after'      => 'after',
    'firstChild' => 'first_child',
    'lastChild'  => 'last_child',   // camelCase keys ONLY
);
if ( ! isset( $position_mappings[ $position ] ) ) {
    continue;   // ← invalid values are silently skipped. No warning, no log.
}

Live bug we hit: writing "last_child" (snake_case) passed registration but produced an empty block_hooks array at runtime. Diagnosed by dumping WP_Block_Type_Registry at runtime, fixed by reading L738.

03Security — The Four Gates shipped in the vote endpoint

Every field in the request lifecycle gets a gate, and each gate blocks a specific attack:

LifecycleGateBlocks which attack
Firing the requestnonce (X-WP-Nonce header)CSRF — forged submissions
Before reaching the endpointpermission_callback → current_user_can()Privilege escalation
Inputabsint() for numbers / sanitize_text_field() for text / kses for rich textDirty data & injection input
Database write$wpdb->prepare()SQL injection
Outputesc_html() / esc_attr()XSS

Nuance that earns points: public operations (anonymous voting) use __return_true + nonce; admin operations require capability checks. Gate strength follows the nature of the operation. And field type picks the sanitizer: absint for numbers, sanitize_text_field for text — three guards, three sheaths, never mixed.

04wpautop — Corrected by Reading Source blocks.php L2528–2552

The rule

Blank line → <p>. Single newline → <br>. (Not "beatify" — beautify. Third time this typo appeared. It's in the permanent log now.)

What do_blocks actually does when content contains blocks

// blocks.php L2526–2529 — inside do_blocks():
if ( false !== $priority && doing_filter( 'the_content' ) && has_blocks( $content ) ) {
    remove_filter( 'the_content', 'wpautop', $priority );
    add_filter( 'the_content', '_restore_wpautop_hook', $priority + 1 );
}

// L2545 — the restore hook:
function _restore_wpautop_hook( $content ) {
    add_filter( 'the_content', 'wpautop', $current_priority - 1 );  // back to 10 — but 10 already passed this round
    remove_filter( 'the_content', '_restore_wpautop_hook', $current_priority );
    return $content;   // unmodified — the hook only restores the chain state
}
Correction issued — against me, by the learner, with source
I (the AI) initially taught that "dynamic block output must be compact to survive wpautop". The learner opened blocks.php, found the remove/restore logic, and disproved it: when content contains blocks, wpautop is removed from the chain entirely — dynamic block output is structurally immune. Compact output remains good hygiene, but it is not load-bearing. wpautop issues only exist in non-block, classic content (classic-editor posts, shortcodes in plain text).

05The Evolution Strategy: Meta Now, Table Later read one, sort the other

OperationIndex pathSpeed
get_post_meta( 40, 'wpex_helpful_up' )WHERE post_id = 40 AND meta_key = '…' → indexed hit, one rowfast ✅ (V0.1 does only this)
ORDER BY meta_value+0 DESC (a "Top 10 helpful" page)meta_value is LONGTEXT, no index → read-sort-everythingslow ❌ (triggers the migration)
Interview answer, final form
"For V0.1, post meta is the right call: the counts are per-post data, and I only read them by post ID, which hits the indexed lookup. I'd move to a custom table only when a feature needs to query or sort by vote count across all posts — then I'd migrate the counts into a dedicated table with proper indexes. So: post meta now, custom table when querying becomes a feature."

06WooCommerce Data Architecture — One save(), Three Tables verified live: DESCRIBE wp_wc_product_meta_lookup

$product->set_price( 99 );   // memory only — the DB doesn't know yet
$product->save();
  ├ ① wp_posts                    // identity & main content — the anchor
  ├ ② wp_postmeta                 // elastic attributes (_price, _sku, plugin data)
  └ ③ wp_wc_product_meta_lookup   // query copy: min_price DECIMAL(19,4) + MUL index, stock_quantity + MUL…

Two layers by design: posts/meta are the content layer (the source of truth — WP ecosystem compatible: wp_query, REST, SEO plugins all read posts). The lookup table is the query layer (a denormalized copy: trade write overhead for indexed filtering and sorting). The frontend price filter hits lookup.min_price — a real DECIMAL column with an index — never the LONGTEXT meta_value.

Frontend mirror: main database + search index. You write once, queries run against the indexed copy. When our helpful block grows a "most helpful posts" page, the official lookup-table pattern is the reference implementation sitting in our own database.
