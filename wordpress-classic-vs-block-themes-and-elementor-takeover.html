Classic vs Block Themes & the Elementor Takeover

Two theme models, one the_content filter — and why Elementor-rendered pages have no blocks, no anchors and no Block Hooks.

Study date: 2026-11-09  ·  Verified on local install: Astra 4.12.7 (classic) · Twenty Twenty-Five (block) · Elementor free
Method: read source with file:line evidence → inspect live page HTML/computed styles → confirm behavior under Xdebug

1Classic vs Block Theme — Who Actually Builds the HTML

The visible difference on a simple page can be zero (both output the same <table> for a table block), but the mechanism is completely different: a classic theme executes PHP to build the skeleton, a block theme stores text containing block markers and lets the interpreter render it.

Classic chain (Astra)

wp-includes/template-loader.php:132 does include $template; — with Astra active that is astra/page.php. astra/header.php:61 calls astra_header(), which prints the builder markup; the whole <head>/<body> document is hand-written PHP. Menu locations come from astra/inc/admin-functions.php:28–43 (register_nav_menus([primary, secondary_menu, mobile_menu])) — that registration is what makes "Appearance → Menus" exist at all. The binding lives in the theme_mods_astra option: nav_menu_locations = { primary: 59, secondary_menu: 59 }.

Block chain (Twenty Twenty-Five)

wp-includes/template.php:66 hands the resolved template to locate_block_template(). wp-includes/block-template.php:65 gates on current_theme_supports('block-templates') — for Astra this fails and the PHP path is returned untouched; that gate is the fork between the two worlds. For TT5 the block template's text is stored at block-template.php:110 in $_wp_current_template_content, and block-template.php:138 returns wp-includes/template-canvas.php instead of any theme file. The canvas (template-canvas.php:12) calls get_the_block_template_html() and builds the entire document itself.

The header itself is only references: twentytwentyfive/templates/page.html:1 → <!-- wp:template-part {"slug":"header"} /-->; twentytwentyfive/parts/header.html is one line → <!-- wp:pattern {"slug":"twentytwentyfive/header"} /-->; the real blocks are in twentytwentyfive/patterns/header.php:15–32 — a group with core/site-title and core/navigation (line 24). That wp:navigation has no ref, so WordPress auto-created a wp_navigation post (id 4) and fell back to a page list.

One sentence: a classic header is PHP code running; a block header is text being interpreted. Classic keeps structure in code and data in options; block keeps structure itself in editable data.

2The Slot in the Middle Belongs to Core, the Frame Belongs to the Theme

Whatever the theme model, the body slot is produced by core/post-content: wp-includes/blocks/post-content.php:43 reads the stored post_content, and line 50 runs apply_filters('the_content', $content). The theme template contributes the frame (wp_head, header, footer, global styles); core contributes the middle by executing the the_content pipeline. This is why "theme switch changed nothing" on a page whose content is not theme-dependent — the middle is identical, and a plain table has almost no theme-styled surface.

3Elementor: Compiled Content Published Through Its Own the_content Filter

Elementor (free, no Theme Builder) does not store blocks. The design lives in postmeta _elementor_data; post_content is almost empty. At render time Elementor hooks the_content and replaces the whole value with its compiled HTML:

StepLocationWhat happens
Priorityelementor/includes/frontend.php:33 + :324THE_CONTENT_FILTER_PRIORITY = 9; registers apply_builder_in_content
Replacefrontend.php:1105–1110get_builder_content() compiles elements; $content = $builder_content discards whatever earlier filters produced
Stripfrontend.php:1328–1341Removes wpautop, shortcode_unautop, wptexturize for the rest of this chain (restored on the next call at :1521–1527)

Consequence 1 — no blocks in the output, so no block anchors

The final HTML is Elementor's compiled markup, not block markup. do_blocks (priority 9) may run first in registration order, but its result is thrown away by the replacement. Anything that exists only in block form — block anchor IDs set in the block editor, block wrappers, block styles — simply is not part of an Elementor page.

Consequence 2 — Block Hooks never survive

apply_block_hooks_to_content_from_post_object runs at priority 8, so it does fire first and can inject <!-- wp:plugin/block /--> markers. But at priority 9 $content is overwritten wholesale, so those injections are discarded. On Elementor-rendered pages Block Hooks are effectively a no-op.

Consequence 3 — typography filters are skipped, but shortcodes/srcset still run

The removal list is exactly three callbacks (frontend.php:1329–1333): wpautop, shortcode_unautop, wptexturize. do_shortcode (11), wp_filter_content_tags (12) and convert_smilies (20) are not removed and still run on Elementor's HTML.

Consequence 4 — the theme still owns the frame

Elementor only owns the content slot. wp_head/wp_footer, theme CSS and the template's header/footer still come from the theme; the page template (Canvas vs Full Width) decides whether the theme frame participates at all.

4Case Study — the Two Navigation Systems That Look Like One

With TT5 active and Elementor on the home page, the visible header navigation was an Elementor widget bound to nav_menu #59. The Site Editor's "Navigation" entity was a separate wp_navigation #4 created from the theme's header pattern with a page-list fallback. Editing #4 in the Site Editor saved fine and changed nothing on the front page — the theme's navigation block was simply not the one being rendered there.

When "saving succeeds but nothing changes", the first question is not "is the cache stale?" but "am I editing the data that the render path actually reads?" Elementor pages answer that question with _elementor_data + nav_menu, not with post_content blocks or wp_navigation.

5Verifying It Yourself with Xdebug

  • Break at wp-includes/template-loader.php:132 and inspect $template: Astra → themes/astra/page.php; TT5 → wp-includes/template-canvas.php (the .html file is never included — it is read as a string).
  • Break on the the_content filter loop and expand $wp_filter['the_content']: it is a live subscription list, not the fixed core default list. Plugins add entries at runtime; equal priorities run in registration order.
  • On an Elementor page, step into frontend.php:1094 and watch $content: at line 1108 it is replaced by compiled HTML; has_filter('the_content','wpautop') is then false for the rest of the chain.
  • Trigger with ?XDEBUG_TRIGGER=1 (trigger mode on port 9003).

6Key Takeaways

  • Classic theme = PHP builds the document; block theme = core canvas interprets block text. The fork is current_theme_supports('block-templates') at block-template.php:65.
  • Same nav menu exists in two incompatible models: nav_menu (classic) and wp_navigation (block). Theme switch swaps which model is live.
  • core/post-content just reads post_content and runs the_content — it does not care what generated the markup.
  • Elementor publishes compiled HTML through the_content at priority 9 and discards earlier filter output → no blocks, no block anchors, Block Hooks are no-ops; wpautop/texturize/shortcode_unautop are stripped for that chain.
  • "Saved but nothing changed" = wrong data source, not necessarily caching. Check which layer the visible markup came from.
