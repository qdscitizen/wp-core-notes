WordPress 缓存机制 · 面试梳理

主题：meta 缓存 / 查询缓存 / 版本号 / Redis / 面试怎么考

0一句话总纲

写一次 meta，会动两套缓存：删掉这篇文章的 meta 缓存，同时推动全站查询缓存的版本号。前者代价小（重查一行），后者代价大（重查全站列表）。

wp_postmeta 表
├── meta 缓存（组 post_meta，key = post_id）→ 靠精确删除失效
└── 查询缓存（组 post-queries，key 含查询参数）→ 靠版本号失效

1update_post_meta 那一刻，发生了什么

一行代码，干了三件事：

// 你写的：
update_post_meta( $post_id, 'count', 5 );

// 实际发生：
1. UPDATE wp_postmeta ...                        // 你要的
2. wp_cache_delete( $post_id, 'post_meta' )      // 删本条 meta 缓存
3. 触发 updated_post_meta 钩子
   → wp_cache_set_posts_last_changed()
   → wp_cache_set_last_changed( 'posts' )        // 版本号 +1

源码位置（WP 7.0）：wp-includes/meta.php:329、wp-includes/post.php:8410

2两套缓存，两条失效路径

对比meta 缓存查询缓存
缓存组post_metapost-queries
缓存 keypost_id（整篇 meta 一条）查询参数（列表查询一条）
失效方式精确删除 wp_cache_delete版本号对比 last_changed
谁失效get_post_metaWP_Query
重查代价索引一行（毫秒）join + 排序 + count（重）
常见误区：「版本号变了，get_post_meta 也要重查」。不对——get_post_meta 不看版本号，只看自己那篇的 meta 缓存有没有被删。

3版本号机制：WP_Query 怎么知道缓存过期了

WP 6.9 起用「salted cache」：key 不变，版本号存在缓存值里，读的时候对比。

// 写缓存时：版本号塞进值里
wp_cache_set_salted( $key, $data, 'post-queries', $last_changed );
// → 实际存：{ data: [...], salt: "1700000000" }

// 读缓存时：版本对不上 = 当没有
wp_cache_get_salted( $key, 'post-queries', $last_changed );
if ( $salt !== $cache['salt'] ) return false;
// → miss → 执行 SQL 重新查 → 用新版本号写回

源码：wp-includes/cache-compat.php:214 / 244（@since 6.9.0）

要点：缓存条目没被删，它还在。只是「出厂日期对不上」，读的时候不敢用。就像 React Query 的 stale 判断。

6.8 及以前是「版本号拼进 key」——key 变了、旧 key 变垃圾。6.9 改成同 key 比版本，Redis 不会堆僵尸 key。

4为什么列表查询贵

// 单条 meta：走 (post_id, meta_key) 索引，命中一行
SELECT meta_value FROM wp_postmeta
WHERE post_id = 123 AND meta_key = 'count';

// 列表查询：多表 join + 排序 + 分页 + 还要算总数
SELECT wp_posts.* FROM wp_posts
  LEFT JOIN wp_term_relationships ...
  LEFT JOIN wp_term_taxonomy ...
WHERE post_type = 'post' AND post_status = 'publish'
ORDER BY post_date DESC LIMIT 10 OFFSET 0;
// 外加一条 COUNT(*) 算总页数

前端类比：byId[123].count（O(1)）对比 all.filter().sort().slice()（O(n log n)）。

5什么时候该建独立表

需求结论
只存 / 读单篇计数meta 就够
要按值排序 / 聚合（热门榜、总票数）必须独立表（meta_value 是 LONGTEXT，无索引）
要原子自增（高并发投票）独立表 votes INT 自增最干净（update_post_meta 是读-改-写，会丢票）
高频写入污染全站查询缓存独立表（写入不碰 posts 版本号）
面试口径：「post meta now, custom table when querying becomes a feature.」——不说「我直接写 SQL 绕开」，那是绕过问题；迁表是解决问题。

6Redis 和 object-cache.php 是什么

默认情况：对象缓存只活一个请求

WP 自带的对象缓存是 PHP 进程内的一个数组（WP_Object_Cache）。请求结束，数组销毁——访客之间不共享。所以默认情况下，列表查询缓存基本只服务同一个请求内的重复查询。

Redis 改变什么

在 wp-content/object-cache.php 放一个文件（drop-in），WP 启动时早期加载它，接管所有 wp_cache_* 函数 → 缓存从「进程内存」搬到「Redis 服务器」。

默认装了 object-cache.php + Redis
存储位置PHP 内存数组Redis 服务器
跨请求❌ 请求结束即销毁✅ 所有访客共享
列表缓存效果基本没用访客 A 查过，访客 B 直接命中
三个 drop-in：object-cache.php（对象缓存）、advanced-cache.php（页面缓存）、db.php（数据库层）。它们都在普通插件之前加载。
关键结论：「投票打穿列表缓存」这个性能问题，只在装了 Redis 的站才严重——因为缓存是跨请求共享的。没装 Redis 的站，缓存本来就活不过一个请求，失效无所谓。

8面试怎么考这部分

高频1. 「How does WordPress keep the object cache fresh after content changes?」

答：「Meta writes fire hooks like updated_post_meta, and core updates a last_changed timestamp in the posts cache group. WP_Query builds its cache key from that timestamp — or in 6.9+, stores it as a salt and compares on read — so every old query cache entry becomes invalid at once. It's a version number instead of deleting entries one by one. And per-object meta cache is separate: it's deleted precisely by post ID.」

高频2. 「Why do I see stale data after I updated meta directly in the database?」

答：「Because the standard API wasn't used — raw SQL doesn't fire the meta hooks. The per-post meta cache wasn't deleted, and last_changed wasn't bumped, so both caches keep serving old data. The fix is to call clean_post_cache( $post_id ) after the raw query.」

中频3. 「A post goes viral and the whole site slows down — why?」

答：「Every vote calls update_post_meta, which bumps the last_changed version — so every WP_Query cache entry on the site becomes stale at once. On a site with Redis, that means the shared list cache keeps getting invalidated and the database gets hit over and over. For high-frequency counters I'd move them to a dedicated table so writes don't touch the posts cache group.」（这题答出来是加分档）

中频4. 「What's the difference between page cache and object cache?」

答：「Page cache stores the finished HTML and serves it before PHP even boots — it lives in a drop-in, advanced-cache.php. Object cache stores query results and data inside PHP, so the page is still built each time, but the database isn't hit. With Redis, object cache is shared across requests; without it, it only lives for one request.」

深挖5. 「What are drop-ins?」

答：「Special files in wp-content that load before regular plugins — object-cache.php for Redis, advanced-cache.php for page caching, db.php for the database layer.」

满分心法：这组题的分不在背参数，在说清「两条失效路径并存」——精确删除（单对象）+ 版本号（查询结果）。大多数候选人只知道其中一个。你能说出「get_post_meta 不看版本号」，面试官就知道你读过 core。
